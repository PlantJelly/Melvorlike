## D005 — 2026-09-11: Farming reuses the skill/tool engine instead of a bespoke passive system

- Decision: `farming` is a normal `SkillId` included in `playable` (level/exp curve, tool tier, sidebar entry all come free from existing generic code). Only the *content page* is special-cased: `App.tsx` routes `farming` to a dedicated `FarmingView` instead of the generic `ProductionView`, because farming's plant/wait/harvest interaction doesn't fit the single active-action-slot pattern the other skills share. A new `Model.farmPlot` field (one plot) advances every tick via `advanceFarm`, independent of `currentAction`, and caps at the crop's grow duration until manually harvested — matching the game design's "passive skills run in parallel with the one active skill" rule.
- Rationale: reusing `toolTiers`/`skills`/`speedMultiplier` for farming means tool crafting, leveling and future food/tool bonuses work for free with zero new code, consistent with the project's stated principle of reusing existing level/tier systems instead of inventing parallel ones (see game_design.md's rejection of a separate mastery system).
- Alternatives considered: a fully separate `CropDB`/plot-tools schema outside `ResourceDB`/`SkillId` (rejected — duplicates the tool-tier and leveling code for no benefit); auto-repeating plant+harvest like the active-action loop (rejected — the requested "최소 루프" is explicitly plant→wait→harvest as three manual steps; auto-cycling is listed as a later upgrade in content_spec.md, not part of this task).
- Caution: `begin()`/`ProductionView` are never called with a farming crop id by any current UI path (the farming page renders `FarmingView`, not `ProductionView`), but the engine does not defensively block it — if a future UI change accidentally renders `ProductionView` for `farming`, a crop could be "gathered" via the single active-action slot in addition to the plot, double-counting production. Keep the `page() !== 'farming'` guard in `App.tsx` if `ProductionView` is ever refactored.
- **Resolved 2026-09-11 (ranching review round 2, finding 6):** this caution turned out to also apply to `decodeSave`'s `currentAction` validator, which the reviewer independently found unguarded. Rather than special-case a second passive skill the same way, `begin()`, `decodeSave`, and `App.tsx`'s routing all now check membership in a single `passiveSkills: SkillId[]` export (`src/content/resources.ts`) instead of comparing against the literal `'farming'`/`'ranching'` strings. The engine-level gap is closed; the UI-level guard is now provably redundant defense-in-depth rather than the only thing preventing double production.

## D006 — 2026-09-11: Farming seed/produce simplification for the minimal loop

- Decision: each crop is a single `ResourceDB` item that is both the purchasable "seed" (via the pre-existing but previously unused `buy` price field) and the harvested produce — planting consumes 1, harvesting returns a fixed yield (3) of the same item. One plot only; no fertilizers; no auto-plant/auto-harvest.
- Rationale: content_spec.md's separate seed-item + fertilizer + multi-plot design is explicitly marked as a later-upgrade layer ("업그레이드로 자동 파종/수확 해금"), not part of the requested minimal loop. Reusing one item avoids a second inventory-item family (seed vs. produce) for a feature whose acceptance criteria only asked for the four-step loop to work end-to-end with save migration and offline/online equivalence.
- Alternatives considered: distinct seed items with partial-return-on-harvest (closer to content_spec's long-term vision) — deferred because it requires the fertilizer system (회수비료) to be meaningful and would otherwise just be a seed you always have to rebuy at a loss; multiple concurrent plots — deferred as an explicit non-goal of "최소 루프".
- Caution: when farming/ranching output is connected to cooking (PROGRESS Planned item 3), revisit whether "seed = produce" still holds once crops are consumed by recipes at a different rate than they're replanted — may need to split seed and produce at that point. This is a provisional-balance decision, not a confirmed requirement (see D004's caution about docs/content_spec.md).

## D007 — 2026-09-11: Ranching is a continuous cycle engine, not a plant/harvest clone, with a hard anti-backlog cap

- Decision: unlike farming's single grow-then-manually-harvest plot, `game_design.md`'s "자동형" ranching (buy once, feed keeps it running, no manual collection step) is modeled as a repeating-cycle process — mechanically closer to `advanceSegment`'s recipe-limited repeated production than to `advanceFarm`'s single-shot grow. `advanceRanch` (`src/engine/model.ts`) computes completed cycles by floor-division (no per-cycle loop, matching the codebase's existing "계산, 반복 없이" convention), consumes feed and produces output for as many cycles as both elapsed time *and* available feed allow, and — when feed is the limiting factor — **caps the carried-over progress at exactly one cycle's duration** rather than letting unproduced time accumulate.
- Rationale: without the cap, an animal left unfed for a long time would bank unlimited "backlog" (since progress is unbounded pre-cap while feed=0), and the instant the player added even 1 unit of feed, all that banked time would be available to cash in — turning feed into a currency completely decoupled from real elapsed time and breaking the cycle-time pacing the whole passive-skill design relies on. Capping at exactly one cycle means: no backlog ever accumulates beyond "one production's worth is ready and waiting," and feeding the animal resumes production on the very next tick with no lost real time beyond what already elapsed unfed — matching game_design.md's "손해 없이 쉬는 상태" requirement precisely (not a full stop requiring a manual restart like `advanceSegment`'s recipe-exhaustion path, and not an exploitable infinite bank either).
- Alternatives considered: mirroring `advanceSegment`'s behavior exactly (null out ownership / require a manual "재개" action when feed runs out) — rejected because it contradicts game_design.md's explicit rejection of click-based ranching maintenance ("쿨타임 수동 클릭 방식은 기각"). Letting progress accumulate unboundedly while unfed — rejected as the exploit described above. A per-cycle loop (`while` producing one at a time) — rejected in favor of the codebase's established closed-form floor-division style for performance on long offline gaps and consistency with `advanceSegment`/`advanceFarm`.
- Caution: this was designed proactively from farming review's findings (the ETA-ignores-speed bug and the missing epsilon tolerance) rather than discovered after the fact — `ranchRemainingMs`/`ranchStarved` divide by `speedMultiplier` and use the same `1e-7` tolerance as `farmReady`/`advanceSegment` from the start. Verify this holds if a third passive-skill cycle mechanic is ever added; consider extracting a shared "capped cycle" helper if a third one duplicates this logic rather than copy-pasting a third time (see D005's reuse rationale).

## D008 — 2026-09-11: One instance per animal type; feed items are farming's existing crops

- Decision: buying an animal is a one-time, permanent unlock (`Model.ranch: Record<animalId, progressMs>`, key presence = owned) rather than purchasing a stackable headcount. Feed is exactly the existing farming crops (wheat, carrot) — no new "sold at market" feed item family. Animal products (egg/wool/milk) are ordinary `ResourceDB` rows with `skill: 'ranching'`, reusing `reqLevel`/`baseDurationMs`(as cycle time)/`exp`/`sell` exactly as farming's crops reuse those fields for grow time — see D005/D006's precedent.
- Rationale: content_spec.md's headcount-scales-with-ranching-level design and per-animal capacity are explicitly a later-upgrade layer, not part of the requested minimal loop's acceptance criteria (buy → feed → output → safe-stop). Reusing farming's crops as feed directly implements game_design.md's explicitly stated "사료는 농사 작물을 소비 — 농사↔목장이 서로 이어짐" cross-skill loop with zero new content, and is exactly the kind of acceptance-criteria item PROGRESS flagged for this task ("농사/제작과 재료를 공유할 때 시간 순서 및 중복 소비 검증").
- Alternatives considered: stackable headcount per animal type (content_spec's actual design) — deferred as an explicit non-goal of "최소 루프", same reasoning as farming's single-plot decision (D006). A dedicated feed item bought from a market — deferred because no market/buy-arbitrary-item feature exists yet, and content_spec's feed choice (밀/당근) already matches farming's existing crops exactly, so introducing a parallel feed item would just duplicate what farming already produces.
- Caution: "시간 순서 및 중복 소비 검증" (chronological ordering / double-spend check when resources are shared) was a specific PROGRESS acceptance item. In this implementation there's no actual double-spend risk to verify: `harvest()` is a manual, discrete `mutate()` call (never invoked during `advance()`'s elapsed-time batch), so a crop can never be "produced" mid-`advance()` and consumed as ranch feed within that same batch — farming only ever adds wheat/carrot to inventory synchronously outside of `advance()`. If farming ever gains an automatic (non-manual) production path, revisit whether `advanceFarm` and `advanceRanch`'s single elapsed-time batch could let the same tick's newly-grown crop be double-counted as available feed before it's "really" available.

## D009 — 2026-09-11: Farming/ranching → cooking recipes reuse the existing speedBonus mechanic; exp-boost food deferred; no new automation

- Decision: added 5 of content_spec.md §2's 6 not-yet-built recipes (야채죽, 나무꾼 도시락, 광부의 스튜, 대장장이 정식, 축제 요리), consuming farming crops (potato/carrot) and ranching products (egg/milk) exactly as `ResourceDB` recipe ingredients, with `FoodDef` entries using the existing single `speedBonus`-per-skill-list mechanic — zero engine changes. The spec's 달걀찜 ("경험치 획득 +10%", an experience-gain buff rather than a speed buff) is deliberately **not** implemented: `FoodDef`/`speedMultiplier`/`addExperience` have no notion of an exp-multiplier food today, and adding one is new engine surface, not a recipe. The 3 existing fish-only recipes (구운 생선/민물 생선탕/훈제 연어) are untouched. For "전 스킬" (all-skills) recipes, `food.skills` is set to the `playable` array from `src/content/resources.ts` rather than a hand-enumerated list.
- Rationale: `speedMultiplier`'s food-bonus check (`food?.skills.includes(skill)`) is already fully generic over `SkillId`, so passing `playable` for an all-skills buff automatically covers `farming`/`ranching` too with no special-casing — confirmed by direct browser observation that eating 야채죽 shortened both an active skill's (벌목) and a passive skill's (농사) displayed time by exactly 5%. Reusing `playable` instead of writing out all 7 skill names also means a future 8th skill is automatically included in "전 스킬" recipes without touching `foods.ts`. Deferring 달걀찜 keeps this task's diff to pure content (matching D005/D006/D008's minimal-loop precedent) rather than mixing in a new buff-type feature; the task's stated scope was connecting farming/ranching *output* to cooking; add exp-boost food as its own task if wanted.
- Automation review (this task's acceptance criteria asked to evaluate need, not to build it): no automation was added for farming/ranching/cooking. content_spec.md §12 already defines the intended automation path (a guild-shop "자동 채집 장치" purchase at skill Lv50, out of scope — guild doesn't exist yet, PROGRESS item 4) and D005/D006/D007/D008 already deferred auto-plant/harvest and per-animal headcount. Cooking itself doesn't need new automation: it already uses the same single active-action slot as every other active skill (begin/advance/craft), and adding two more ingredient sources (crops, animal products) doesn't change that mechanic's shape. Revisit only if real play reveals a specific friction point (e.g. juggling 5+ ingredient types manually feels tedious) — no such signal exists yet since this is unplaytested.
- Caution (resolves D006's forward-caution): D006 asked whether "seed = produce" (one item serves as both plantable seed and harvested output) still holds once crops are consumed by recipes at a different rate than replanted. It holds fine mechanically — recipes just spend inventory like any other ingredient, no special handling needed — but it does mean a player who eats into their crop stock via cooking has less surplus available to replant *or* sell, a balance interaction that hasn't been playtested. Not a defect, just unverified balance; note for whoever eventually plays through the full economy.

## D010 — 2026-09-11: Guild scoped to the exchange system only; quests deferred; `buyCrop` generalized into `buyResource`

- Decision: implemented only game_design.md §3's 환전소 (exchange/catch-up shop) — buy any already-unlocked raw material with gold, and exchange a higher-tier raw material down to its skill's Lv1 baseline at a rate of `1.5^tierGap` (floored), gated by a new standalone `Model.guild` tier (0-indexed into `guildTiers`, upgraded with a flat gold cost mirroring `toolTiers`'s pattern). The 일일퀘스트/마일스톤퀘스트 (daily/milestone quest) system — game_design.md's other named guild feature, and the literal mechanism it describes for gaining guild levels ("완료 시 골드+자재로 길드 레벨업") — is **not implemented**; guild leveling here is a direct gold-only "후원" purchase instead. Also generalized `buyCrop` (farming-only, added in D006) into `buyResource` (any raw material, i.e. any `ResourceDB` entry with no `recipe`), used by both the new guild page and farming's existing "씨앗 구매" button (`FarmingView`'s call site was left unchanged — only the function it calls, via `actions.ts`'s `buySeed` wrapper, was repointed).
- Rationale: PROGRESS's acceptance criteria for this task named only "하위 재료 구매/교환" (low-tier purchase/exchange) plus verifying "순환 거래 이득 방지" and "낮은 티어 접근성" — the exchange system is literally what game_design.md calls "the real purpose of the old '의뢰' concept," while quests are a separate onboarding/guide feature with their own scope (daily rotation state, milestone tracking, new UI) not named in this task's criteria. A minimal gold-cost tier progression (identical shape to `toolTiers`/`upgrade()`) was the smallest way to make the exchange depth gate ("길드 Lv1~9/10~19/20+" in content_spec.md §5) actually reachable and testable, rather than leaving `ExchangeDB`'s 2/3-tier-gap entries permanently dead content behind a guild level that can never change. Generalizing `buyCrop`→`buyResource` avoided two near-duplicate "buy a raw material for gold" functions (the guild's requirement is a strict superset of what `buyCrop` already did) and, as a side effect, closed a real pre-existing gap: `buyCrop` never checked the buyer's skill level against `reqLevel` (only the UI disabled the button) — `buyResource` enforces it at the engine level, consistent with the defense-in-depth lesson from the farming/ranching reviews (D005's resolution note).
- Alternatives considered: quest-driven guild leveling (content_spec's actual design) — deferred as a distinctly larger, separately-scoped feature; per-material or percentage-based exchange rates instead of the uniform `1.5^tierGap` — content_spec.md §5 states this ratio explicitly ("한 티어 내려갈 때마다 수량 x1.5배"), so it was implemented as specified rather than reinvented. Exchanging between arbitrary tier pairs (e.g. hardwood→oak) instead of always down to the Lv1 baseline — rejected for the same reason D008 picked one canonical feed target per animal: a full N×N tier graph is unbounded complexity for a "최소" task, while "everything reduces to the skill's Lv1 material" is a single, easy-to-reason-about rule that still satisfies the catch-up/accessibility goal (a player short on any tier of a material can always fall back to buying/holding the Lv1 version). `iron`'s exchange target was chosen as `stone` (not `copper`) purely because `stone` is mining's Lv1 material and copper is also Lv1 (parallel, not a tier below iron) — documented here since it's not obvious from the code alone.
- Caution: "순환 거래 이득 방지" (circular-trade profit prevention) is verified two ways in `src/engine/guild.test.ts`, both worth preserving as regression guards if `ResourceDB` sell prices or `ExchangeDB` entries ever change: (1) every baseline target (wood/stone/fish_small) has no `ExchangeDB` entry of its own, so no reverse path exists structurally — exchange is a one-way DAG, not a cycle; (2) for every current `ExchangeDB` entry, `exchangeRate^tierGap * sell(target) < sell(source)`, i.e. exchanging then reselling the result always nets strictly less gold than selling the source directly, for the *current* sell-price dataset — this is a property of today's numbers, not something the engine enforces structurally, so a future rebalance of sell prices could silently violate it if that test isn't kept green. `buyResource`'s new `reqLevel` check is a behavior change for farming crops too (previously `buyCrop` had no level gate at all); no existing caller relied on buying a not-yet-unlocked crop, and the full test suite (including farming's existing tests) still passes, but flagging it here since it wasn't purely additive.

## D011 — 2026-09-11: Accessory rerolls use one deterministic-effect option per permanent slot and filtered probability weights

- Decision: the common accessory system has exactly three permanent slots (crown/necklace/ring). Each slot is crafted once at stone material, then promoted through copper/iron/gold by consuming only the next tier's cost; promotion mutates only `tier`, preserving the rolled option and rarity. A reroll consumes one enchantment stone and replaces one option plus its rarity. The provisional option pool is all-skill speed, all-skill experience, and sale-value bonus; rarity controls magnitude. These effects are deterministic after the user-triggered reroll, so elapsed-time production remains closed-form and online/offline equivalent.
- Probability rule: use content_spec.md §7's enchantment-stone weights, discard rarity columns above the accessory material's cap, then renormalize the remaining weights. A stone-grade accessory rerolled with a gold-grade stone therefore rolls low/medium at 15:20, not by clamping every higher result to medium. Enchantment stones below the accessory material tier are rejected before consumption.
- Supply/cost scope: added the smallest playable supply chain needed by game_design.md — four existing-spec herbs as farming crops, mana stone and gold ore as direct mining resources, gold ingot as blacksmithing output, and four magic recipes for enchantment stones. The planned vein-event mechanic is still absent; direct mining is an explicit minimal-loop substitute. Slot names, exact costs, option magnitudes, and one-option-per-slot are provisional because the source docs specify none of them precisely; all are isolated in `src/content/accessories.ts`/`resources.ts` for later balancing.
- Save/architecture: save v7 adds the magic skill/tool plus an exact three-key accessory record. v1~v6 migration defaults these fields; v7 validation rejects unknown slots, invalid option/rarity pairs, rarity above the current material cap, and material tiers above the saved blacksmithing level. RNG is injected only into the reroll function for boundary tests and never enters timed production.
- Alternatives considered: porting the legacy per-skill equipment inventory and deterministic legendary selection — rejected because it contradicts the new three-common-slot, one-item-per-slot direction; runtime chance effects such as double yield/material saving — deferred because they would require a new deterministic random-stream design to keep long offline batches equivalent to short ticks; implementing mining vein events first — deferred as a separate planned mining extension.
- Caution: adding gold ore to `ExchangeDB` extends the existing one-way mining exchange graph by a two-tier path to stone. The anti-resale-profit regression test covers it. Exact economy balance and the direct-mining mana-stone substitute remain unplaytested.

## D012 — 2026-09-12: Save backup/restore reuses `decodeSave` as the only gate and doubles as corruption recovery

- Decision: `encodeSave` (new, `src/engine/save.ts`) is a trivial `JSON.stringify` of the live `Model`; the settings-page download button offers exactly that string as a file. Restore (`restoreFromBackup`, `src/state/gameState.ts`) does not add a parallel validation path — it feeds the chosen file's text straight into the existing `decodeSave`, and only on success does it replace `state()`, persist, and (critically) clear the module-local `blocked` flag that `load()` sets when the stored save fails to parse. A failed restore returns `decodeSave`'s thrown message and leaves the current save/state untouched. The UI requires a `window.confirm` before ever calling restore, since it is an overwrite.
- Rationale: `decodeSave` already is the project's one true "is this a valid save" check (used for both the stored localStorage value and, from now on, an arbitrary uploaded file) — a second bespoke validator would duplicate every version-migration branch and could drift out of sync with it. Wiring restore to also clear `blocked` turns backup/restore into the concrete recovery path for the corruption-protection behavior AGENTS.md and DECISIONS/HANDOFF have flagged since the project's start ("corrupt data currently blocks automatic writes") — previously that block had no in-app recovery at all, only starting over on `initial()`.
- Alternatives considered: a dedicated "import" schema/validator separate from `decodeSave` — rejected, no behavioral difference from reusing it and strictly more surface to keep correct across future version bumps. Silent/no-confirm restore — rejected as a plain destructive overwrite of the only save a browser-local game has; `window.confirm` was chosen over a custom modal component since the project has no modal pattern yet and this is a rare, one-off confirmation, not recurring UI.
- Caution: this does not address multi-tab save contention (still unsupported, tracked separately) — restoring in one tab while another tab's autosave interval is live can still be overwritten by that other tab, the same class of issue observed firsthand during earlier browser verification. `gameState.ts` remains untested by `npm test` (consistent with the rest of the localStorage-touching state layer); only `save.ts`'s `encodeSave`/`decodeSave` round-trip is unit tested, the download/restore UI flow itself is browser-verified only (see docs/implementation_status.md).

## D013 — 2026-09-12: Backup checksum is a soft, non-cryptographic deterrent, not tamper-proofing; clipboard export added alongside file download

- Decision: `encodeSave` now appends a `checksum` field (FNV-1a hash of a key-sorted canonical JSON string of the model) to the saved JSON. `decodeSave` verifies it **only when present** — a save with no `checksum` field (every save written before this change, and any hand-built test fixture) is accepted exactly as before; a save that has a `checksum` field whose value doesn't match the rest of the content is rejected with a dedicated error. No `Model.version` bump was needed since the checksum is an envelope concern, not game state, and this "soft" rule needs no migration: old saves simply lack the field and skip the check.
- Rationale: user feedback after testing raised two points — (1) the browser's native "Save As" dialog on download isn't something the app can suppress (a page cannot control this; it's the browser's own download-location setting), so a clipboard-copy alternative was added alongside the file download rather than replacing it; (2) even for a single-player game with no leaderboard/PvP, casually editing an exported save (e.g. changing `"gold":1000` to `"gold":12391` in a text editor) felt too easy and the user asked for friction against exactly that. A "soft" checksum directly defeats that scenario — the exported file's checksum no longer matches once any field is hand-edited — while requiring zero schema migration and zero changes to the ~6 existing test files that construct raw save JSON by hand via plain `JSON.stringify(...)` instead of `encodeSave` (those fixtures simply have no checksum field and are unaffected, verified by the full 78/78 suite passing unchanged). Because `decodeSave` is shared by both the backup-restore path and the normal localStorage autosave/load path, this also raises the bar on directly hand-editing `localStorage` via devtools, which was flagged during the same conversation as an existing, unaddressed loophole.
- Alternatives considered: a hard/required checksum gated by a `Model.version` bump to 8 — rejected as disproportionate churn (would force updating every hand-constructed "current version" test fixture across farm/ranch/guild/food/accessory/model test files to route through `encodeSave`, for a feature explicitly scoped as a deterrent, not real security) for the same net protection against the stated threat (casual text-editor tampering), since a hard requirement is trivially bypassed by simply deleting the `checksum` key anyway. A real cryptographic signature (HMAC with a secret) was not considered further — the secret would have to ship in client JS, so it provides no more real security than the current hash while being more code; this was explicitly communicated to the user as a limitation of any client-side scheme.
- Caution: this is explicitly **not** tamper-proofing — the hash algorithm ships in the client bundle, so anyone willing to read `src/engine/save.ts` and recompute a matching checksum (or simply delete the `checksum` field to fall back to the pre-existing soft/unchecked path) can still produce an accepted, edited save. `src/engine/save.test.ts` has a test that documents this exact boundary (a checksum-stripped, tampered save is still accepted) so the limitation stays visible and regression-tested rather than silently assumed. If real tamper resistance is ever wanted, it requires server-side validation; this project has no backend today (static Vite/Solid frontend, `localStorage`-only persistence) and adding one — for cloud save/sync or otherwise — is a separate, much larger architectural decision not made in this session (see PROGRESS.md's Planned list).
- Post-review fixes (same day, independent review round): the initial implementation gated verification on `typeof raw.checksum === 'string'`, which meant a checksum field present but coerced to a non-string type (e.g. hand-edited to a bare number) silently skipped verification entirely instead of being rejected — tightened to gate on the field's mere *presence* (`raw.checksum !== undefined`), requiring it to be a matching string once present. Separately, `canonical()`'s treatment of a hypothetical `undefined`-valued field diverged from `JSON.stringify`'s real behavior (which drops `undefined` object values and nulls them in arrays), which — had a future optional `Model` field ever existed — could have made `encodeSave` produce a checksum that mismatches its own output and reject a perfectly valid save on the very next load; `canonical()` now mirrors `JSON.stringify`'s exact `undefined` handling. Both were found by independent review (not observed in practice — `Model` has no optional fields today) and are now regression-tested. A remaining design caution, deliberately not acted on: because `encodeSave`/`decodeSave` is the single path shared by both routine localStorage autosave/load and explicit backup restore, any *future* such divergence bug would risk resetting every player's routine save (via the `blocked`/corruption path) rather than only failing the rare, user-confirmed restore action — scoping the checksum to backup files only would contain that blast radius but was judged disproportionate restructuring for a deterrent-only feature, especially now that the concrete divergence found this round is fixed at the root.

## D014 — 2026-09-12: Multi-tab save sync via the `storage` event, not a leader-election lock

- Decision: `src/state/gameState.ts` adds a `window.addEventListener('storage', ...)` listener. Whenever `SAVE_KEY` changes in `localStorage` — which per the DOM spec only fires in *other* same-origin tabs, never in the tab that made the write — the receiving tab checks its own `document.visibilityState`. A **visible** tab does not adopt the incoming value at all; it immediately calls `saveGame()` to re-assert its own current state over whatever was just written (a no-op if `blocked`, preserving corruption protection). Only a **hidden** tab decodes the new value via `decodeSave`, calls `advance(s, Date.now())`, clears `blocked`, and adopts it via `setState(s)`. An invalid external write (parse/validation failure) is caught and ignored either way, leaving that tab's own state untouched. The shared `decodeSave` + `advance(s, Date.now())` step is factored into one `decodeAndAdvance()` helper used by `load()`, `restoreFromBackup()`, and this listener, returning `{s, n}` so callers that want the catch-up count (`load`, `restoreFromBackup`) can use it and the listener (which intentionally stays silent for a background tab) can ignore it.
- Rationale: the concrete, previously-documented problem (see D012's caution, README, and this session's own browser-verification notes) is that an idle/background tab's periodic `saveGame()` can silently overwrite a fresher save written by another tab or process, with total, unexplained data loss as the only symptom. The `storage` event is the simplest primitive that directly detects this. The **visibility gate was added after an independent review round found the first version of this fix could cause the exact inverse bug**: without it, a stale background tab's routine 10-second autosave (or its own `visibilitychange`/`pagehide` flush, fired at precisely the moment a human switches attention *toward* another tab) could silently overwrite a currently-focused tab's newer, unsaved progress — the review noted this collision is structurally frequent, not a rare race, because the flush is triggered by the very act of switching tabs. Gating on visibility fixes both directions with one rule: "the tab nobody is looking at defers to whichever save it last sees; the tab someone is looking at defends its own current reality." `document.visibilityState` was chosen over `document.hasFocus()` for consistency with the codebase's one existing precedent for this exact "is a human looking at this tab" question (`gameLoop.ts`'s `visibilitychange` flush already uses it) and because `hasFocus()` only reflects OS-level window focus, which is a stricter and less relevant signal here (e.g. it's false for every tab when the browser itself isn't the focused application, which shouldn't disable a visible tab's own protection).
- Alternatives considered: a leader-election / single-active-tab pattern (only the visible/focused tab runs the game loop and autosaves; background tabs pause) — rejected as a bigger change with a real regression risk: the existing `visibilitychange`/`pagehide` flush (`gameLoop.ts`) deliberately persists a tab's progress the moment it becomes hidden, and gating that on visibility would silently break exactly the case it exists for. Comparing `lastSaveTime` between tabs to decide which one is "newer" — rejected as unsound: every open tab's `lastSaveTime` independently converges toward `Date.now()` via its own 200ms `tick()`, regardless of whether a human is actually using that tab, so it does not distinguish "the tab with the player's real actions" from "an untouched idle tab" the way it might first appear to. `document.hasFocus()` instead of `visibilityState` — tried first, then rejected: in addition to the consistency/relevance reasoning above, this session's own browser testing tool reported `hasFocus() === false` for every tab simultaneously (no true OS window-focus model in that automated environment), making `visibilityState` also the more testable signal, though production browsers do implement `hasFocus()` correctly — the switch was made on the merits above, not merely to work around the test tool.
- Scope, explicitly: this is conflict *prevention* (stopping the silent, one-sided overwrite), not multi-tab *support*. If a player genuinely takes divergent actions in two tabs within the same short window before either autosaves, those actions are not merged — whichever tab's `storage`-event-driven sync (or manual save) lands last wins, same as today, just no longer silently and unpredictably. README/AGENTS.md's existing "다중 탭 동시 플레이 미지원" framing is updated to describe this more precisely rather than removed, since true concurrent-tab support (e.g. via CRDT-style merge) remains out of scope.
- Caution: unverified live in this session — the specific case of a `blocked` (corrupted-load) tab recovering via another tab's valid write. The code path is identical to the already-verified `restoreFromBackup` recovery (decode succeeds → `blocked = false` → `setState`), and the listener's success path (including that exact line) was directly observed executing correctly during the sync tests above, so this is inferred from code-path equivalence rather than an isolated repro — a clean repro was impractical in this session because the existing `pagehide` flush (any live tab, on navigating away) tends to "self-heal" an externally-corrupted `localStorage` value before a fresh reload's `load()` can observe it. Not unit-tested (`gameState.ts` remains browser-verified only, consistent with every other localStorage-touching function in this file) — no `vitest` environment with `window`/`StorageEvent` is configured, and adding one was judged out of scope for this task.
- Second independent review round (after the visibility-gate fix above) found and left open as non-blocking, deliberately not fixed: (1) `localStorage.clear()`/`removeItem` fire a `storage` event with `key: null`/`newValue: null`, which the `!e.newValue` guard silently ignores — meaning another open tab's next autosave could "resurrect" a deliberately-cleared save; not fixed because no save-reset feature exists anywhere in the app yet to make this concrete, and the correct behavior for a future reset feature (should other tabs also reset, or defensively restore their own copy?) is a product decision, not a code bug, to make when that feature is built. (2) The module-level `storage` listener has no `removeEventListener`/dedup guard, unlike every other `addEventListener` in this codebase (`gameLoop.ts` pairs each one with `onCleanup`) — not fixed since the risk (duplicate listeners from re-evaluating this module in the same JS realm) is latent and unconfirmed under the project's actual dev setup (no `import.meta.hot` usage anywhere in `src/`, so Vite's editing this file most likely falls through to a full page reload, not a scoped HMR re-execution).

## D015 — 2026-09-12: Guild daily quests reuse the exchange/production stack; reward is gold-only, not a new "guild exp"; content is deterministic per day

- Decision: implements only the **일일퀘스트** (daily quest) half of game_design.md §3/content_spec.md §5's "일일퀘스트 + 마일스톤 퀘스트" pair. Each real UTC day (`dayId(time) = Math.floor(time / 86400000)`), `Model.dailyQuests` is replaced with 3 fresh "deliver N of resource X" quests — completed or not, they are simply swapped out on the next day with no carry-over or penalty. Candidates are drawn only from raw materials (`!r.recipe`) the player has already unlocked at generation time (`s.skills[r.skill].level >= r.reqLevel`), matching the guild page's existing "재료 구매" section's same unlock rule. Completing a quest (`completeDailyQuest`, keyed by index **and** `resourceId` — see post-review fix below) spends the required amount from inventory and pays `dailyQuestReward()`: `floor(amount * sell * 2 * (1 + accessoryBonus(s,'sale')))` — the same "sale" accessory bonus and rounding `sell()` already applies, shared by the engine and `GuildView`'s reward preview so the two can't drift. Quest content is generated by a tiny seeded xorshift32 PRNG keyed only on the day id (`seededRandom`, in `model.ts`), not `Math.random()`, so the same day + same unlocked-resource set always produces the same 3 quests.
- Rationale: content_spec.md §5 explicitly marks "구체 퀘스트 목록/보상 밸런스 — 미정" (undecided), so there was no fixed list to implement faithfully; a generic "deliver N of an unlocked resource" template was chosen as the smallest thing that satisfies the design's stated shape (recurring, resource-delivery-based, gold+guild-progress reward) without inventing specific quest flavor text the source docs never committed to. The reward was simplified to gold-only rather than the design's literal "골드 + 길드 경험치" — introducing a second, guild-specific currency/leveling-track would duplicate what `guildTiers`/`upgradeGuild` (D010) already does with plain gold, and D010 already made the same simplification call for guild-level-up itself; keeping quests gold-only avoids reopening that already-settled scope decision. Determinism (seeded-by-day instead of `Math.random()`) was chosen to match this project's established "결정론적 시간 정산" principle (D003) and, concretely, to keep two independently-constructed same-day game states directly comparable in tests (`model.test.ts`'s online/offline-equivalence test constructs two separate `initial(0)` models and asserts they're deeply equal after parallel play — true `Math.random()` would have broken that test's premise, not just this feature's own tests).
- Alternatives considered: **마일스톤 퀘스트** (the one-time, onboarding-flavored half of the same design section) — deferred to a separate atomic task. Nine of its ten example milestones (content_spec.md §5) can be checked from state this codebase already tracks persistently (skill level thresholds, `tools[skill] > 0`, `ranch` having any key, skill `exp`/`level` as a proxy for "ever done X"), but two (첫 채집, 길드 환전소 첫 이용) have no reliable persistent proxy and would need new explicit one-shot tracking flags, and the tenth explicitly requires "도감(정착민)" — a system D004 already flagged as an unconfirmed suggestion, not approved scope. Bundling all of that into this task risked exactly the oversized-task problem AGENTS.md's atomic-development section warns against. A wholly custom quest-content list (unique flavor per quest, matching content_spec's 10-example milestone style) was considered for the daily quests too — deferred for the same "undecided in source docs" reason as the reward split; the generic delivery template can be replaced or extended later without a schema change (`DailyQuest` only needs `resourceId`/`amount`/`done`).
- Save/architecture: bumps `Model.version` to 8 (a genuine schema addition, unlike D013's checksum envelope) — `dailyQuests: {day: number; quests: DailyQuest[]}`. v1–v7 saves first receive the new field from `initial()`, then regenerate today's quests after the saved skill levels have been restored so migrated players use their actual unlocked-resource pool. A v8 save must contain exactly 3 quests with distinct resource ids; every quest must resolve to a raw material unlocked at the restored skill level, have an integer amount from 5 through 15, and have a boolean completion flag. This enforces the same invariants as generation. Same-day level gains do not invalidate an already-loaded quest because validation runs only while decoding the save and skill levels never decrease.
- Caution: reward balance (the ×2 sell-price multiplier, and the 5–15 delivery-amount range) is provisional and unplaytested, consistent with every other economy number in this project. `refreshDailyQuests` runs unconditionally inside `advance()` on every `mutate()`/`tick()`, so it executes far more often than it actually changes anything (a cheap integer comparison each time) — negligible at this `Model` size, matching prior rounds' efficiency findings on this same file. Determinism means every player who is on day N with the same unlocked-resource set sees the *same* 3 quests — acceptable for a single-player, local-only game with no shared server state, but would need revisiting (a per-player seed component) if this project ever gained any multiplayer/leaderboard dimension.
- Post-review fixes (same day, independent review round, 8 findings): (1) migrating a pre-v8 save generated its initial `dailyQuests` from `initial()`'s default level-1 skills, *before* `decodeSave`'s own loop a few lines later restored the save's real skill levels — a high-level player's post-migration quest pool was silently restricted to level-1-unlockable resources until the next day rollover. Fixed by regenerating `dailyQuests.quests` (via the now-exported `generateDailyQuests`) immediately after the skills-restoration loop, so v<8 migrations see the pool their *real* levels unlock. (2) `completeDailyQuest` originally identified the quest to complete by array index alone; since `refreshDailyQuests` can wholesale-replace the array inside the very `mutate()` call a click triggers (a UTC-day rollover landing mid-click), the index could point at a different quest than the one the button displayed. Fixed by requiring the caller to also pass the `resourceId` it rendered, rejecting the completion if the quest at that index no longer matches — the click then safely no-ops instead of silently completing the wrong quest. (3) the reward formula omitted the `sale` accessory bonus `sell()` already applies to the same kind of gold-for-resource payout, and used `Math.round` instead of `sell()`'s `Math.floor` — fixed by extracting a shared `dailyQuestReward(s, quest)` (now used by both `completeDailyQuest` and `GuildView`'s preview, closing a related UI/engine-drift finding from the same review). (4) `refreshDailyQuests` read the raw, un-clamped `time` argument to `advance()` rather than the already-clamped `s.lastSaveTime` the rest of that function treats as authoritative, so a backward clock jump could make the quest-day clock diverge from the production clock and spuriously discard the current day's (possibly completed) quests — fixed by passing `s.lastSaveTime` instead. (5) `decodeSave`'s v8 validation didn't reject duplicate `resourceId`s across a save's 3 quest slots despite `generateDailyQuests`'s own no-duplicate invariant — fixed with a `seen` Set check alongside the existing per-quest validation. Left unfixed as non-blocking: quest-pool determinism is keyed to `ResourceDB`'s current iteration order, so a future content reorder could silently change what "day N's quests" means for past days (no version-pinning exists for this, same class of fragility as any other content-order-dependent code in this project); and the custom xorshift32 PRNG, while correct and tested, is more machinery than a simpler seeded approach would have needed — not revisited given the working implementation carries no known defect.

## D016 — 2026-09-14: Milestone readiness is derived from permanent progress; only claims and first exchange need storage

- Decision: add the nine currently representable milestone examples from content_spec.md §5 in their documented order and omit only "도감(정착민) 첫 등록", whose underlying system remains unapproved and unimplemented. Each completed milestone pays a fixed, provisional amount of gold once through an explicit claim action. No guild experience, material reward, or second guild progression track is introduced, continuing D010/D015's existing simplification.
- State model: readiness is calculated from state that already persists and cannot regress: gathering/cooking/farming/magic skill progress, skill levels, crafted tool tiers, and owned ranch animals. `Model.milestones.claimed` stores only claimed ids. A successful exchange has no durable trace in the old model, so `exchangeUsed` is the sole new event flag and is set only after inventory mutation succeeds. Failed exchanges cannot unlock the milestone.
- Save architecture: save schema v9 adds `{claimed: MilestoneId[]; exchangeUsed: boolean}`. v1–v8 saves keep all prior state, start with no claimed rewards, and can immediately claim milestones inferred from restored permanent progress. Prior exchange use cannot be reconstructed honestly, so migrated players must perform one new successful exchange for that milestone. v9 validation rejects unknown or duplicate ids, malformed flags, and claimed milestones whose permanent condition is not satisfied.
- Rationale: storing only irreducible facts avoids nine parallel booleans drifting away from the actual game state and lets existing players receive credit for visible progress without a migration guessing at inventory they may already have sold. Explicit claiming keeps rewards visible as onboarding feedback and prevents save migration from silently changing gold.
- Caution: milestone rewards (100–5,000 G) are unplaytested balance. The first cooking/farming/magic milestones use `level > 1 || exp > 0`; this remains valid while those skills gain experience only from their named production action. If future mechanics grant those skill experience through unrelated actions, introduce explicit event flags rather than weakening the milestone meaning.

## D017 — 2026-09-15: 왕국 복원이 주 진행이며 정리·공사는 스킬이 아니다

- Decision: 기본 진행을 스킬 목록 해금이 아니라 왕국 구역 프로젝트로 구성한다. 프로젝트는 조사, 폐허 정리, 부분 자재 납품, 복원 공사, 완료 순서로 진행한다. 폐허 정리와 복원 공사는 경험치·레벨·전용 장비가 없는 왕국 활동이며 생산과 같은 전역 액티브 슬롯을 쓴다.
- Rationale: 복원 결과가 새로운 스킬·구역·시설을 여는 구조가 게임의 고유한 목적과 가이드라인을 동시에 만든다. 정리와 공사를 각각 스킬로 만들면 레벨이 없는 유사 진행 바가 늘고, 레벨을 부여하면 복원보다 반복 숙련 자체가 목적이 된다.
- Alternatives: 스킬을 처음부터 모두 보여주는 방식, 폐허 회수/건설을 별도 스킬로 만드는 방식, 길드 퀘스트만으로 온보딩하는 방식을 검토했다. 왕국 프로젝트가 핵심 테마를 화면과 진행 양쪽에서 가장 직접적으로 보여주므로 선택했다.
- Caution: 필수 프로젝트는 희귀 확률 보상, 만료, 실패, 진행도 손실을 사용하지 않는다. 이전 저장은 이미 열린 기능을 잠그지 않으며 대응 프로젝트 보상을 중복 지급하지 않는다.

## D018 — 2026-09-15: 병렬 자동 생산과 확률 정착민을 기획에서 제외한다

- Decision: Lv50 자동 채집 장치와 여러 스킬 동시 생산은 채택하지 않는다. 후반 편의는 전역 액티브 슬롯을 유지하는 반복, 목표 수량, 다음 작업 예약, 프리셋으로 제한해 검토한다. 멜버의 스킬링 펫과 역할이 같은 확률 정착민도 채택하지 않는다. 이 결정은 D009에 기록된 당시의 자동 채집 장치 제안을 대체한다.
- Rationale: 병렬 생산은 매직 리서치식 효율 최적화 압박을 만들고 처음 합의한 한 액티브 작업 구조를 약화한다. 확률 정착민은 이름과 테마를 바꿔도 낮은 확률의 영구 스킬 보너스라는 기능이 같아 차별성이 부족하다.
- Alternatives: 높은 레벨에서 스킬별 자동 장치를 구매하는 방식, 이름 있는 주민을 낮은 확률로 수집하는 방식을 기존 초안에 두었다. 편의 기능과 왕국 복원/수집 기록으로 각각의 목적을 더 직접적으로 해결한다.
- Caution: 농사와 목장의 패시브 진행은 기존 합의이며 병렬 자동 생산 제외 대상이 아니다. 도감과 업적의 구체 내용은 전체 생산망 이후 다시 설계한다.

## D020 — 2026-09-15: 두 번째 구역(부서진 다리) 추가 — 버전 게이팅, 선행조건 없음, 확장된 검증은 보류

- Decision: `ProjectDef`에 `introducedVersion`을 추가해(부서진 다리=11, 대장간=10) 저장 검증이 "이 저장 버전에 등장해야 할 구역 집합"을 동적으로 계산하게 했다(`projectIds.filter(id => ProjectDB[id].introducedVersion <= version)`). 저장 v10→v11 이전 시 아직 도입되지 않은 구역은 검증 대상에서 제외되고 `initial()`이 만든 기본값(조사 가능·미시작)이 그대로 남는다 — 스킬 추가 때 반복돼온 `if (version < N && id === 'x') continue` 패턴을 프로젝트에도 그대로 적용한 것. 구역 간 하드 선행조건(예: "대장간을 끝내야 다리가 보인다")은 만들지 않았다 — 대신 다리의 납품 자재에 벽돌(대장작업 산출물)을 포함시켜, 정리까지는 재료 없이 가능하지만 실제 완료는 대장간을 먼저 끝내야만 가능하도록 재료 의존성으로 자연히 유도했다.
- Rationale: v1~v9→v10 이전(D019)은 "이미 열려 있던 기능을 잃지 않는다"였지만, v10→v11처럼 **왕국 시스템이 이미 있던 저장에 새 구역이 추가되는 경우는 반대 방향 규칙**이 필요하다 — 기존 플레이어도 새 콘텐츠는 직접 플레이해야 한다(자동 완료 금지). 두 규칙이 공존해야 하므로, `version < 10`(왕국 시스템 자체가 없던 시절)과 `version >= 10`(왕국 시스템은 있었지만 이 구역은 없던 시절)을 구분하는 게 핵심이다 — 이미 존재하던 `version < 10 ? unlockedGame() : initial()` 분기가 정확히 이 구분과 일치해서 추가 코드 없이 그대로 맞아떨어졌다(v1~v9 이전 테스트로 확인: 그 시절엔 애초에 잠금 자체가 없었으므로 다리도 대장간과 함께 자동 완료됨 — "이미 열려있었다"가 맞는 서술). 하드 선행조건을 만들지 않은 이유는 구역이 2개뿐인 지금 단계에서 `ProjectPhase`에 `locked` 상태를 추가하고 프로젝트 간 의존성 그래프·해금 전이 로직을 만드는 비용이, "재료로 자연히 유도"라는 이미 있는 매커니즘보다 크다고 판단했기 때문 — 구역이 늘어나 순서 제어가 실제로 필요해지면 그때 다시 검토한다(D017의 "짧은 직선형" 의도와 완전히 일치하진 않지만, 재료 의존성만으로도 실질적 순서는 지켜짐).
- Alternatives considered: 해금 목록의 반대 방향 검증(모든 `unlockedSkills`/`unlockedFeatures` 항목이 시작 스킬이거나 완료된 프로젝트로 설명 가능해야 한다)을 저장 검증에 추가하려 했으나, `unlockedGame()`(요리·농사·목장·마법 등 아직 어떤 프로젝트도 부여하지 않는 스킬까지 전부 미리 열어주는 기존 테스트 전용 기준 상태)이 이 검증과 정면으로 충돌해 기존 테스트 10여 개가 깨졌다 — 되돌렸다. 그 스킬들을 실제로 여는 구역(무너진 식당/버려진 밭/낡은 축사/쓰러진 마법탑)이 전부 구현된 뒤에야 이 방향의 검증이 `unlockedGame()`과 충돌 없이 의미를 가질 수 있다.
- Caution: `KingdomView.tsx`의 완료 카드/복원 힌트 문구를 프로젝트별 하드코딩(이전 리뷰의 비블로킹 발견)에서 `unlockSkills`/`unlockFeatures` 기반 문구로 일반화했다 — 이후 구역을 추가할 때 이 부분은 더 손댈 필요가 없어야 한다. 다음 구역(무너진 식당)을 추가할 때는 `introducedVersion`을 다음 정수로, 그리고 위에서 되돌린 반대 방향 검증을 이번엔 추가해도 되는지(그 구역이 여는 스킬이 `unlockedGame()`에서도 다른 구역으로 설명 가능해지는 시점) 다시 판단할 것.

## D021 — 2026-09-16: 세 번째 구역(무너진 식당) — 순수 패턴 재적용, 반대 방향 검증은 계속 보류

- Decision: `ruined_restaurant`(`introducedVersion: 12`, `unlockSkills: ['fishing']`이 아니라 `['cooking']`)를 D020과 완전히 같은 패턴으로 추가했다. 납품 자재에 피라미(낚시 산출물)를 넣어 다리를 먼저 끝내야 유도되게 한 것도 다리가 벽돌로 대장간을 유도한 것과 동일. 엔진(`model.ts`)·UI(`KingdomView.tsx`) 코드는 **한 줄도 바뀌지 않았다** — `save.ts`의 버전 배열 확장과 `Model.version` 숫자만 올리면 끝이었다. 이는 D020에서 설계한 `introducedVersion` 기반 검증과 `unlockSkills`/`unlockFeatures` 기반 UI 문구 일반화가 실제로 반복 재사용 가능함을 확인한 결과다.
- D020의 남겨둔 질문("반대 방향 검증을 이번엔 추가해도 되는지")에 대한 답: **아직 아니다.** `unlockedGame()`은 여전히 농사·목장·마법을 어떤 프로젝트도 아직 부여하지 않은 채로 미리 열어주므로(버려진 밭/낡은 축사/쓰러진 마법탑 미구현), 반대 방향 검증을 추가하면 D020에서 겪은 것과 같은 이유로 기존 테스트가 깨진다. 이 세 구역이 전부 구현된 뒤에만 이 검증을 안전하게 추가할 수 있다 — 그때 다시 판단.
- Caution: 다음 구역(버려진 밭 또는 낡은 축사 또는 쓰러진 마법탑, 순서 미확정)을 추가할 때도 이 문서의 패턴(콘텐츠 항목 + `introducedVersion` + 저장 버전 배열 확장 + 회귀 테스트 3~4개)만 반복하면 될 것으로 예상된다. 세 구역이 모두 끝나면 위 반대 방향 검증 추가를 반드시 재검토할 것 — 잊지 않도록 여기 남긴다.
